# 工具参数异常导致审查终止的修复记录

## 背景

2026-09-16 在部署环境对 UF 仓库 MR !4 进行联调。GitLab webhook 接收、项目归属和失败评论回写均成功，但模型调用 CI 与仓库工具时，会话因 `state.input: expected record, received string` 终止。

## 根因与边界

- AI SDK 在参数解析或 schema 校验失败时仍产生 `invalid` 工具调用事件，参数可能是字符串、数组或 null，而会话工具状态要求对象。
- 处理器直接持久化该参数，导致普通工具输入错误升级为整个会话失败。
- 自动工具修复无条件转发到 `invalid`，但受限 GitLab 会话没有这个工具。
- 本次不放宽 GitLab 工具白名单，不解析字符串后绕过原工具 schema 执行，不修改模型配置，也不覆盖原失败记录。

## 已完成

1. 无效 SDK 调用持久化为工具错误；非对象参数在状态层使用空对象，原始 SDK 错误保留用于模型纠正。
2. 成功与失败事件写入参数也经过对象边界检查；工具执行和权限仍由原有 SDK 与工具层负责。
3. 仅在当前工具目录实际提供 `invalid` 时使用该回退工具；大小写修复同样限制在当前目录内。
4. 无效调用保留重复调用检测，不因错误恢复绕过循环保护。
5. 新增真实 SDK 流到会话持久化的回归测试，覆盖无效 JSON、字符串、null、数组、schema 不匹配及后续正确调用。
6. 新测试加入运行时 CI，并由 CI 契约测试固定入口。
7. 首次复测进一步发现循环检测按默认可见性查找 agent，无法取得推荐型 GitLab coordinator；修复为包含已注册的推荐型和声明型 agent，权限仍由该 agent 的当前规则控制。
8. 对无效原始参数使用摘要区分重复调用，避免不同坏参数都存为 `{}` 后被误判为相同调用；测试验证不同输入不误判、连续相同输入仍触发检测。
